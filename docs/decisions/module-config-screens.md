# Module Config screens — separate surfaces, live editing

**Status:** accepted (2026-07-27) — design locked (grill-with-docs session),
**circle ① implemented on 2026-07-27** (presence declaration `editor_screens`,
table `server_editor_screens` + WS relay `config_read`/`config_write` with no
storage, generated editor screens + "Data" fallback, canvas Data panel reduced
to binding, Shop declaring its two screens). Complements the ADR
`composable-data-models` (whose location for the generated form it revises).

## Context

In the canvas Data panel, the shop catalog appeared twice: as "Project data"
(the `data/categories/*.yaml` files, editable) and as "Server sources"
(`boutique:items` / `boutique:categories`, derived runtime views with computed
fields `final_price`…). Two approaches were grilled: ① unify the schemas (a
single model where some fields are marked `runtime`, not editable); ② separate
the *surfaces* by task. Approach ② wins: the confusion came from mixing
"manage my module's content" and "bind a menu to a source" in the same
surface — resolving it with nesting/provenance would have *explained* the
duplication with subtle UI machinery instead of removing it. The `runtime` flag
becomes useless (no form shows those fields any more; they only live in the
binding directory).

## Decisions

1. **Surfaces separated by task.** A Table with a **module-declared** model is
   edited in the module's **Config screens**; the canvas Data panel goes back
   to being a pure *binding* surface: project-authored sources + the directory
   of server sources (schema + live preview, read-only). Module data appears
   there only through a "Managed by module X" link. *Rejected:* nesting server
   sources under project data by provenance (`derivedFrom`), and the
   `runtime: true` flag in `model/v1`.

2. **Screens generated by the core, declared by the module — never coded.** The
   module declares its screens through the presence channel (like models and
   sources):
   > **Revised by the ADR `yaml-assisted-editing` (2026-07-27)**: "a Table/
   > Config **with a declared model**" is no longer a prerequisite. The schema
   > becomes a progressive enhancement — a screen can edit a file **without a
   > schema** (literal fields inferred from the values), and every screen
   > offers two modes on the same file (form + raw YAML). The "preserving YAML
   > editing" prerequisite of §4 for circle ③ is **bypassed** rather than paid:
   > the YAML tab writes verbatim to a foreign file, and the form is read-only
   > there.

   ```yaml
   editor_screens:
     - id: catalog
       label: "Catalogue"        # plain string; i18n later
       table: data/categories    # the Table/Config with a declared model being edited
   ```

   Each screen = a label + a Table/Config; the core generates the form
   (master-detail if the root is a list, simple form if the root is an object —
   the form generator of `composable-data-models` §7, repositioned as a
   "generic schema-driven config editor"). Sidebar: the module entry carries
   its screens (the canvas "Editor" entry disappeared on 2026-10-18: a module's
   project is listed with the others, see the amendment of the ADR
   `addon-owned-project-roots`). **Fallback**: declared models + a dedicated
   project without `editor_screens` ⇒ an auto-generated "Data" screen (one
   entry per Table). Custom `FrontendModule.routes` remains possible for an
   exotic case, but is not the normal path. *Rejected:* a single imposed "Data"
   tab (`?tab=` overlay) — the module organizes its screens itself.

3. **Live-only editing through the WS relay.** The screen reads the files on
   open via the WS hub and writes directly (the plugin writes the file +
   reload); greyed out "server offline" otherwise. The backend **relays without
   storing** — no backend copy specific to these screens. For an Artisan
   add-on project, the direct WS write does not bypass sync: it lands on disk
   like a manual edit and the P3b scan/auto-push propagates it normally — no
   new conflict surface. *Rejected:* editing a backend copy re-read on
   reconnect (availability theater).

   > **Revised 2026-07-30 — the write is journaled.** "Relays without storing"
   > left module configs out of the history, while the menus of the same
   > project are in it: the same screen, the same UI, sometimes versioned and
   > sometimes volatile, with nothing to tell them apart. That is exactly the
   > "I expected a history and there isn't one" we wanted to avoid.
   >
   > The rule becomes: **a managed root is a versioned root.** After the
   > plugin's ack, the backend applies the same patch to the project's stored
   > tree and commits (`journalProjectFiles`, `lib/projectJournal.ts` — a
   > single implementation, shared with in-game mutations such as
   > `/boutique additem`), then broadcasts `bundle_available`. That broadcast is
   > not decorative: it makes the plugin refresh `.artisan-sync.yaml`, without
   > which its next scan would see LOCAL_ONLY and push the same content again.
   >
   > Three safeguards: we journal **after** the ack, never before (the history
   > does not tell of a write that did not land); a `project_id` that is not an
   > Artisan project journals nothing and **is not created** (inventing a
   > project would turn a third-party plugin's folder into an Artisan project
   > behind the admin's back) — the response carries `journaled: false`; and an
   > identical rewrite creates no entry (`createCommit` deduplicates by content
   > hash).
   >
   > What does **not** change: reading stays live, the screen stays greyed out
   > offline, the write still goes through the plugin. What makes the revision
   > possible is that disk detection has become reliable (spec
   > `2026-07-30-poll-first-disk-sync-design`): the "availability theater"
   > verdict held when a backend copy would not have been resynchronized with a
   > guarantee.

4. **"Plug Artisan onto what exists" trajectory — three circles.**
   ① Artisan add-ons (owned files, canonical writers) — **the only circle
   built now**; ② existing plugins as a *read-only* form (community schema
   laid down as data); ③ write editing of third-party files. Declarations stay
   pure data (models + screens + future `reload_command`) precisely so that
   ②③ are reachable without redesigning anything. Prerequisites identified
   for ③: **preserving** YAML editing (comments/key order of files we do not
   own) and a careful "external" sync mode (plugins that rewrite their own
   config at runtime make watcher-owning impossible). ②③ = a product in
   itself, to be grilled when a real target plugin exists. A standalone screen
   (a module without a project/canvas) will be a separate route at that time.

### Amendment 2026-10-19 — singleton config: config root and module view

Original question: the configuration of ArtisanDailyRewards (the rewards) exists
only once, must be versioned and deserves a tailored interface. A kind limited
to one instance was ruled out: a kind describes a collection that one creates,
names and references in any project. "One instance" would force choosing the
project that carries it, handling duplicates and deletion, and would add a
cardinality to the registry, the listing, the create and the models. The
singleton config therefore stays a file at the module's root edited by its
screens, already versioned (`config_write` commits and reloads, `VersionRecorder`
records a Version for every root).

Two additions (API 2.7.0, `@artisan/editor-sdk` 1.6.0):

- **Module view.** `screens.declare(id, label, table, projectId, component)`
  names a view of `FrontendModule.screens`. The screen renders it in place of
  the generated form and passes it `ConfigScreenProps` (`value`, `shape`,
  `set(path, value)`, `addRow`, `removeRow`, `readOnly`). The host keeps the
  read, the working copy, the save, the YAML tab and the file's history: the
  view only does the rendering. A key missing from the bundle falls back to the
  generated form.
- **Config root.** `projectRoots.registerConfig(projectId, dir, moduleId)` marks
  the root `role: config` in `project_roots`. The editor removes it from the
  "Projects" list (§2 amended on 2026-10-18): it is reached through the
  module's screens, which carry its per-file history.

Criterion that would bring back the kind: several instances become necessary
(several reward calendars). A module that anticipates it puts a list in its
single file.

### Amendment 2026-10-24 — a screen of the module's folder goes through the draft

Finding (Shop): the "Settings" screen wrote the file to the server with its own
Save button, while everything else in the folder goes through the draft then
Deploy; and its link, outside the project route, closed the folder in the
sidebar. Since `server-disk-only-storage`, a module's folder is a Project like
any other: its `data/` is already in its working copy. A screen whose table
lives in a listed folder therefore opens **in that folder**
(`/servers/$serverId/projects/$projectId/screen/$screenId`) and edits its
working copy: the change goes to the draft and leaves with Deploy, like its
Documents. The folder stays the active project, the sidebar keeps it open. The
YAML tab is not there: the YAML Document writes live, which would be a second
write path. A configuration root (`role: config`), which is not a listed
Project, keeps the standalone page and its live write (§3, amendment
2026-10-19).

Added on 2026-10-28: a source such a screen edits leaves the folder's tree
(`listedDataSources`), as a source a module's model types already did. The
screen's row under the module is its one entry; a second row opened the
generated form beside the module's view. An old `…/data/<id>` link shows the
screen's form.

## Accepted debt / open questions

- **Source schema ↔ model dedup**: `DataSourceDeclaration.schema` (hand-written
  fields) and the declared model coexist — divergence is possible, but it now
  costs only a display inconsistency in the binding directory. Deferred: an
  optional `model: "ns:id"` on the declaration (base = model, `schema` =
  computed extras) will take shape better after the binding of external configs
  (which will often have no source at all).
- ~~**Live-only generalized to the canvas**~~ — **decided on 2026-08-12**,
  grill held, ADR `server-disk-only-storage`: the server becomes the only
  store, §3 above is generalized to the canvas. The owner explicitly gave up
  history and offline editing, which lifted the blocker. Consequence for this
  ADR: the 2026-07-30 revision ("a managed root is a versioned root", backend
  journaling after ack) **falls** with the journal; editing goes from a live
  write to a write on explicit gesture.
