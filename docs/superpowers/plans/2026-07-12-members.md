# Members — invitations & rôles (bloc ③) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Un owner invite son équipe dans son Network (lien partageable + email Scaleway TEM) ; les invités deviennent `member` (édition complète, rien de destructif) ; les checks de rôle passent par une couche de capacités extensible.

**Architecture:** Trois couches. **Capacités** : `lib/capabilities.ts` (`can(role, capability)`) + `requireCapability` dans `membershipGuard` ; les 6 `requireMember(..., "owner")` existants migrent vers la capacité qui correspond à ce que fait chaque handler. **Invitations** : table `network_invites` (code façon `link_codes` : expiry, maxUses, revocable), lib `inviteStorage`, routes owner (CRUD) + publiques (preview/accept), template email `inviteEmail` + extraction du helper `sendSafely` (recommandation de la review du bloc ②, c'est le 2ᵉ consommateur). **UI** : la section « Members — coming soon » de `networks.$networkId.tsx` devient réelle (liste, invite dialog lien+email, revoke, remove, promote/demote avec garde dernier-owner).

**Tech Stack:** Bun + Hono + Drizzle · React 19 + Vitest · infra mail du bloc ② (`lib/mail/`).

**Références:** décisions du grill 2026-07-11 (Q4 : owner/member extensible ; Q5 : lien ET email) ; `CONTEXT.md` entrée **Membership** ; ADR `accounts-only-editing.md`.

## Global Constraints

- Backend : **TOUJOURS `bun run test`, JAMAIS `bun test`** ; changement `schema.ts` → migration `db:generate` committée.
- Éditeur : `npm test` ; strings UI react-i18next (`en.ts` + `fr.ts` même commit) ; design system d'abord (`components/ui/*`, tokens `var(--…)`, pas de hex).
- Rôles : `owner` (tout), `member` (édition seule) ; `admin` = valeur legacy traitée comme `owner` dans la table de capacités (dépréciée, commentée). `requireMember` SANS rôle (le check "est membre") reste le gate d'édition — un `member` a donc automatiquement l'accès édition partout (loader/saver/deploy/assets), c'est voulu.
- Sémantique invite : porteur du lien + compte connecté = peut accepter (l'email d'invitation est un canal de LIVRAISON, pas une restriction d'identité — documenté). Accept idempotent (déjà membre → 200 `already_member`). Garde **dernier owner** : impossible de remove/demote le dernier `owner`/`admin` d'un network (409).
- Un échec d'email ne casse JAMAIS la requête (posture bloc ②) ; l'invitation par email crée TOUJOURS le lien (l'email est un bonus best-effort).
- Docs same-commit : REST → `rest-endpoints.md` ; DB → `entities.md` ; CHANGELOG. Conventional commits, `git add` explicite.
