# VPS Deployment and CI/CD Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deploy Artisan's backend, editor, and PostgreSQL on the OVH VPS behind Cloudflare Tunnel and automatically release every fully validated merge to `main` through Coolify.

**Architecture:** GitHub Actions validates backend, editor, and plugin independently, then a production workflow invokes a small tested Node.js deployment orchestrator. The orchestrator calls the Coolify API through Cloudflare Access, waits for each deployment, and smoke-tests the public service before proceeding. Coolify owns the application containers, database, volumes, logs, and rollback history; Cloudflare Tunnel is the only web ingress.

**Tech Stack:** GitHub Actions, Node.js 22, Bun 1.x, Java 21/Gradle, Docker, Coolify v4, PostgreSQL 16, Cloudflare Tunnel, Cloudflare Access, Ubuntu 26.04.

## Global Constraints

- Keep the existing dirty worktree intact; stage and commit only files named by the current task.
- Never run backend tests with `bun test`; always run `bun run test` so the isolated `artisan_test` database is used.
- Use `editor.artisanmc.net` for the editor and `api.artisanmc.net` for REST, WebSockets, bundles, and resource packs.
- Do not host or deploy the Minecraft server on this VPS.
- Do not expose PostgreSQL, Coolify port 8000, or web ports 80/443 directly from the VPS.
- Keep SSH as the only direct ingress and restrict it with the OVH firewall and UFW when the operator has a stable source IP.
- Keep all Cloudflare, Coolify, database, and application credentials out of Git.
- Deploy backend before editor and stop immediately when a build, migration, deployment, or health check fails.
- Treat Drizzle migrations as forward-only; no automatic down migration or destructive rollback.
- Preserve the Cloudflare per-request upload limit assumption: individual HTTP request bodies remain below 100 MB.
- Use conventional commit messages and run the task-specific verification before every commit.

- [ ] **Step 3: Implement the deployment orchestrator**

Create `deploy/coolify-deploy.mjs`. Validate every required environment variable up front. Use:

```js
const terminalFailures = new Set(["failed", "cancelled"]);

export function buildHeaders(env) {
  return {
    Authorization: `Bearer ${env.COOLIFY_API_TOKEN}`,
    "CF-Access-Client-Id": env.CF_ACCESS_CLIENT_ID,
    "CF-Access-Client-Secret": env.CF_ACCESS_CLIENT_SECRET,
    Accept: "application/json",
  };
}

export async function triggerDeployment(fetchImpl, config, resourceUuid) {
  const url = `${config.COOLIFY_BASE_URL}/api/v1/deploy?uuid=${encodeURIComponent(resourceUuid)}&force=false`;
  const response = await fetchImpl(url, {
    method: "POST",
    headers: buildHeaders(config),
  });
  if (!response.ok) throw new Error(`Coolify deploy request failed with HTTP ${response.status}`);
  const body = await response.json();
  const deploymentUuid = body.deployments?.[0]?.deployment_uuid;
  if (!deploymentUuid) throw new Error("Coolify did not return a deployment UUID");
  return deploymentUuid;
}
```

Implement `waitForDeployment` with 60 attempts and a 10-second default sleep. Treat `finished` as success and `failed` or `cancelled` as terminal failure. Implement `waitForHealth` with 30 attempts, a 5-second default sleep, and success only for `response.ok`. Network errors are retryable but the final error reports the URL. `deployProduction` must call trigger → wait → health for backend, then trigger → wait → health for editor. Never print tokens or request headers.

At module entry, run only when `import.meta.url === new URL(process.argv[1], "file:").href`; call `deployProduction({ fetchImpl: fetch, sleep: ms => new Promise(resolve => setTimeout(resolve, ms)) }, process.env)` and set `process.exitCode = 1` on error.

```yaml
name: Deploy production

on:
  workflow_run:
    workflows: [CI]
    types: [completed]
    branches: [main]

permissions:
  contents: read

concurrency:
  group: production
  cancel-in-progress: false

jobs:
  deploy:
    if: github.event.workflow_run.conclusion == 'success'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.workflow_run.head_sha }}
      - uses: actions/setup-node@v4
        with:
          node-version: "22"
      - name: Reject stale successful runs
        env:
          GH_TOKEN: ${{ github.token }}
          EXPECTED_SHA: ${{ github.event.workflow_run.head_sha }}
        run: |
          CURRENT_SHA="$(git ls-remote origin refs/heads/main | cut -f1)"
          test "$CURRENT_SHA" = "$EXPECTED_SHA"
      - name: Deploy backend then editor
        env:
          COOLIFY_BASE_URL: ${{ vars.COOLIFY_BASE_URL }}
          COOLIFY_BACKEND_UUID: ${{ vars.COOLIFY_BACKEND_UUID }}
          COOLIFY_EDITOR_UUID: ${{ vars.COOLIFY_EDITOR_UUID }}
          API_HEALTH_URL: https://api.artisanmc.net/health
          EDITOR_HEALTH_URL: https://editor.artisanmc.net/
          COOLIFY_API_TOKEN: ${{ secrets.COOLIFY_API_TOKEN }}
          CF_ACCESS_CLIENT_ID: ${{ secrets.CF_ACCESS_CLIENT_ID }}
          CF_ACCESS_CLIENT_SECRET: ${{ secrets.CF_ACCESS_CLIENT_SECRET }}
        run: node deploy/coolify-deploy.mjs
```

Add secrets `COOLIFY_API_TOKEN`, `CF_ACCESS_CLIENT_ID`, and `CF_ACCESS_CLIENT_SECRET`. Give the Coolify API token only the permissions required to deploy and inspect these resources.

- [ ] **Step 2: Protect `main` after CI check names exist**

After one CI run registers the checks, require pull requests and the exact checks `backend`, `editor`, and `plugin`. Require branches to be up to date before merging. Do not enable force pushes or branch deletion.

- [ ] **Step 3: Prove CI blocks a deliberately broken pull request**

On a temporary `codex/verify-ci-gate` branch, make a harmless test assertion fail, open a draft PR, and confirm the matching required check fails and merge is blocked. Revert the deliberate failure, confirm all checks pass, then close the draft PR without merging test-only damage.

- [ ] **Step 4: Prove a real merge triggers sequential deployment**

Merge the production infrastructure commits through a PR. Observe `CI` complete successfully, then `Deploy production` check out the same SHA. Confirm Coolify starts backend first, reports it finished, receives a successful public health check, then starts editor. Confirm both public URLs serve the merged SHA's behavior.

- [ ] **Step 5: Prove deployment failure stops the sequence**

Temporarily set `COOLIFY_BACKEND_UUID` in the GitHub environment to a non-existent UUID, rerun the production workflow, and confirm it fails before any editor deployment request. Restore the correct UUID immediately and rerun successfully. No application source change is required.

- [ ] **Step 6: Verify application rollback**

From Coolify, select the prior editor deployment, redeploy it, and verify the editor remains healthy. Redeploy `main` through the normal workflow afterward. For backend rollback, verify that the prior image can start against the current schema before selecting it; if not, follow the forward-fix policy.

- [ ] **Step 7: Verify database and volume restoration**

Restore the latest PostgreSQL backup into a separate temporary PostgreSQL resource and compare migration state plus representative row counts. Restore `/app/data` into a temporary volume and verify representative custom-item/resource-pack files and checksums. Delete the temporary restore resources only after evidence is recorded in the private operations log.

- [ ] **Step 8: Run final acceptance checks**

Run all repository checks plus public probes:

Expected: all repository checks pass; API and editor are healthy through Cloudflare; every direct web/database port on the VPS is closed or filtered.
